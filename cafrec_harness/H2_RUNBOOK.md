# Testing H2 as registered — runbook (2026-09-21)

**H2.** *LLM-generated temporal user profiles will achieve higher NDCG@10 than
interaction-derived embeddings for users in the lowest quartile of interaction
counts.* The paper currently reports H2 as registered but **not tested**, because
no evaluated profile was generated by a language model. This produces the missing
arm, tests it, and separately tests whether better context engineering changes the
answer.

The Azure VM is not needed. Both content CSVs are public on Zenodo record
`10.5281/zenodo.18159199` (already cited in `04_experimental_setup.tex`), and
every step that touches them runs on Modal, so the 6.9 GB never crosses a
domestic link. **Done 2026-09-21:** downloaded in 9 min, MD5s verified, and the
Pure subsets reproduce the 2026-09-17 audit exactly — first-level category
99.83%, second-level 85.46%, non-empty caption 98.90%, 33 caption rows repaired.
`content_pure/PROVENANCE.json` on the volume records URLs, MD5s and fetch date,
which also answers the `TODO(cite)` on those two files.

## Why there are four prompt variants

For a lowest-quartile user the plain prompt contains five category labels and six
captions, and the category histogram is already what `cat_beyond` encodes. So the
plain profile can only *re-represent* information the harness already has. The
variants are the documented ways out, and running all four separates them.

| arm | what it adds | source |
|---|---|---|
| `plain` | nothing — re-representation only. **The registered arm.** | — |
| `kar` | knowledge in the model's weights: asks it to *infer* subjects, franchises and adjacent content instead of summarising | Xi et al., *Towards Open-World Recommendation with Knowledge Augmentation from LLMs*, RecSys 2024, [arXiv 2306.10933](https://arxiv.org/abs/2306.10933) |
| `collab` | information in the data but not in this user's rows: items watched by their nearest long-history users | Wu, Chang et al., *CoRAL*, KDD 2024, [arXiv 2403.06447](https://arxiv.org/abs/2403.06447) |
| `support` | the same, aggregated: those users' category mixes as in-context examples | prompt-optimisation line, [arXiv 2509.09066](https://arxiv.org/pdf/2509.09066) |

`collab` and `support` are **exploratory, not the registered arm** — a profile
built partly from other users' behaviour is no longer purely this user's temporal
profile, and calling it the registered test would be hypothesis drift.
`analyze_h2.py` applies Holm within the registered family and within the
exploratory set separately, and never pools them.

Related but out of scope for H2, both architecture changes rather than profile
changes: RLMRec ([WWW 2024](https://arxiv.org/abs/2310.15950)) aligns the LLM
semantic space to the collaborative space by cross-view mutual-information
maximisation — CAFREC's single `profile_proj` linear layer is the thin version of
this — and A-LLMRec ([KDD 2024](https://arxiv.org/abs/2404.11343)) aligns CF
embeddings into the LLM's token space. Worth citing as future work.

## Two retrieval failures found and fixed before spending anything

**Item-item co-occurrence returned popularity, not collaboration.** Measured over
400 users: 417 distinct items filled 4,000 retrieval slots, the top item appeared
for 60% of users, mean pairwise overlap of two users' top-10 was 23.5%. Cosine
normalisation did not rescue it — with 651k interactions over 7,164 items,
long-tail co-occurrence is noise and what survives is whatever is popular.
Replaced with user-based retrieval (items from the nearest long-history users,
scored `sum(similarity)/sqrt(popularity)`), which is also what CoRAL actually
does. After the fix: **2,349 distinct items, 2.8% top-item share, 0.4% overlap.**
The failed version stays runnable via `--collab-retrieval item` so the negative
finding remains reproducible.

**The support set was degenerate for the H2 cohort.** A 6-item user's histogram is
a few 1/6 values, thousands of sparse users tie exactly, and the top-5 came back
as five identical copies of the target's own three categories — no information, in
the one cohort it exists to help. Fixed by restricting the neighbour pool to users
with ≥20 training rows (11,574 users) and de-duplicating identical mixes.

Re-check either at any time:

```powershell
.venv\Scripts\python.exe build_h2_prompts.py --variant collab --diagnose-retrieval
```

## Design decisions baked into the code

| Decision | Why |
|---|---|
| Profile rows are `r >= 2` (**all** training rows), not `r >= 22` | The beyond-window rule drops users with ≤22 rows. The H2 cohort is 6,240 users with ≤12 clicks — all would get a zero vector, as `cap_beyond` did, and the test would be vacuous. `r >= 2` still excludes the valid/test holdout, so the profile stays causal. |
| Retrieval excludes each user's own held-out items | Otherwise a retrieved list could name the very item the user is scored on and the profile could describe it. |
| Behaviour block imported from `render_profiles` | Same six fields, same `_bucket` thresholds. The LLM sees what the template profile encodes, so LLM-vs-template isolates the generated text. |
| Profiles in **English**, embedded with `bge-large-en-v1.5` | The template profile uses the same encoder, so the comparison is text-vs-text, not encoder-vs-encoder. (Content profiles used `bge-large-zh-v1.5` because they embedded Chinese captions directly.) |
| Greedy decoding, fixed seed | The corpus is a deterministic function of prompts + model revision; resuming cannot change earlier profiles. |
| Everything at `train_batch_size=512` | The operating point the rest of the ablation-seed results use. `analyze_h2.py` asserts it. |

| Step | Est. |
|---|---|
| 3 generation passes (1.00 + 1.09 + 1.28 = 3.37× plain, ~2.3 h each) | ~$8.50 |
| 3 embedding passes | ~$2 |
| 12 registered training runs | ~$7.20 |
| 9 exploratory runs (kar, support, histgate) | ~$5.40 |

The projection extrapolates from a 64-prompt batch with ramp-up and drain overhead
and almost nothing for continuous batching to work with, so it is an upper bound —
a full queue should beat 2,660 tok/s. The plan can be stopped after any arm.

## Paper changes once it runs

H2 is marked "registered, and not tested in this study" in the abstract,
`01_introduction.tex` (hypothesis list **and** outcome paragraph), the status table
in `04_experimental_setup.tex`, `05_results.tex` § `sec:res:exploratory`,
`06_discussion.tex` (status table, limitations list, and the future-work bullet
"test H2 as registered") and `07_conclusion.tex`. All need revising — a null
result for H2 is as reportable as a positive one and fits the existing framing.

Also settle when writing up:

- the generator is **not** the profile *encoder*; name both models;
- state the `r >= 2` rule and why the beyond-window rule was not used;
- report the retrieval diagnostic: naive item-item collaborative retrieval on
  KuaiRand-Pure returns popularity, which is a finding worth a sentence and bears
  on how CoRAL-style methods transfer to sparse logged data;
- keep `cat_beyond` in the H2 comparison table: for a sparse user the plain LLM
  profile is close to a paraphrase of the category histogram, so `cat_beyond`
  bounds what a positive plain result could mean;
- the `TODO(cite)` on the two content CSVs is answerable — Zenodo
  `10.5281/zenodo.18159199`.
